# Project Documentation Standard

**Applies to:** Every project published in this portfolio, including DFLAB, forensic exercises, research and demonstrations.  
**Version:** 1.0 · **Status:** Active standard · **Owner:** Umar Alfarouq Yusuf

Each published project must provide the sections below. If an item does not apply or work has not reached that stage, state **Not applicable**, **Not yet performed**, or **Pending** rather than omitting it or inventing details. A concise webpage overview may link to controlled reports and supporting files.

## Required project record

1. **Title** — clear project name and project identifier where relevant.
2. **Overview** — brief context and what the project is.
3. **Objectives** — intended outcomes.
4. **Scope** — included work, exclusions, assumptions and limitations.
5. **Tools and technologies** — actual tools, versions, platforms, datasets and dependencies; distinguish proposed from used.
6. **Methodology** — approach and rationale, including relevant controls and reproducibility considerations.
7. **Practical procedures** — steps actually performed, or clearly labelled planned procedures. Include prerequisites, safety/authorization considerations and records generated where appropriate.
8. **Findings and observations** — actual results and observations, including limitations; do not state anticipated results as findings.
9. **Supporting screenshots or evidence** — appropriately sanitized references to genuine evidence. Identify unavailable evidence as pending. Do not fabricate screenshots, logs, test outputs or other evidence.
10. **Report or documentation** — link to the report, procedure, notebook or other project record; state when documentation is pending.
11. **Status** — explicit, accurate project status and date, such as Planned, In progress, Completed, Validated or Archived. Explain status when helpful.

## Exercise and data labels

Clearly label simulated exercises, training datasets, laboratory experiments and demonstrations. State when material is synthetic, intentionally simulated, public training data or a controlled lab experiment. Do not imply that a simulated scenario is a real case or that training observations are real investigative findings. Identify dataset source and applicable licence/terms when known. Protect personal, confidential and case-sensitive information; sanitize public evidence.

## Truthfulness and evidence

- Separate **planned**, **performed**, **reported**, **tested**, **validated** and **approved** work.
- Claims of results must be supported by actual records. Include dates, tool versions and test environment when material to reproducibility.
- Do not fabricate project activity, findings, procurement, screenshots, reports, approvals or validation results.
- If evidence cannot be published, provide a sanitized summary and state that underlying evidence is retained privately, but only when that is true.
- Distinguish tool installation from tool validation and project completion.
- Maintain version, date, author, revision history and classification for formal controlled records.

## Applying the standard to DFLAB

The DFLAB portfolio overview is the high-level project entry; infrastructure sub-records support relevant sections. This standard applies at the project level and should not force every inventory row or administrative form to repeat irrelevant sections. The overall DFLAB entry should link to the applicable infrastructure documents for tools, methods/procedures, observations, evidence, documentation and status. Unknown or unfinished sections remain explicitly pending.
